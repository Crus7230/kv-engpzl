# 7리전 스테이지·난이도 구성

## 1. 현재 기준

Renewal의 정식 캠페인 설계 단위는 다음과 같다.

`Campaign → 7 Region → 지역별 6 Chapter → 챕터별 10 Stage`

총 42챕터·420스테이지이며, 한 스테이지는 문장제 하나와 숫자·기호를 발굴하는 논리 보드 하나로 구성한다. 기존 C01~C03 210개 ID는 보존하고 C04~C06 210개를 나선형 복습 경로로 추가한다.

코드의 단일 진실 원천은 `lib/features/campaign/data/regional_campaign.dart`이다. 모든 스테이지에는 다음 값이 정의되어 있다.

- 안정적인 `skillId`
- 스테이지 제목과 대표 문제·정답식. C04~C06은 아직 원본을 가리키는 제작 슬롯
- 수학·매치·수식 구성·읽기 난도 `M/B/C/R`
- 기준 풀이·탐색 별·실패 한도 `W/P/L`
- 5×5·6×6 독립 fixture ID와 seed
- 튜토리얼·힌트 정책
- 재사용 가능한 `primarySkillId`, 선수·복습 개념과 스테이지 변형 ID
- 선수확인·소개·안내·독립·전이·복습·관문의 학습 역할
- 원본 stage와 실제 콘텐츠에서 산출하는 의미 profile, 카탈로그상 재출현 간격을 가진 계획
- 수학 난도와 분리된 보드 mechanic·지역 skin·도입 역할
- 완료 후 이어질 `nextStageId`와 선택형 추가 해금

원본 청사진 `regionalCampaign`의 420개는 모두 `planned`로 유지한다. 앱이 사용하는 `initialCampaign`은 R1/R2의 실제 120문항을 덧씌운 카탈로그이며, R3~R7의 300개는 여전히 실행할 수 없는 제작 슬롯이다. 개발용 `4×3+2` fixture는 별도 카탈로그에 유지한다. 새 보드 v3와 R2 확장은 실행 검증 전이며 [R2 소스 구현 기록](R2_ALPHA_IMPLEMENTATION.md)에 경계를 정리했다.

2026-10-12 실제 R1 보드 overlay는 `r1_board_progression.dart`로 분리했다. C01부터 직선형을 배우고 C02에서 장애물·L/T형·5매치형, C04에서 2층 봉인·조합을 배운다. 뒤 챕터는 배운 효과를 결합한다. 원본 청사진의 C05 도입표는 기존 제작 구조의 기록이며 현재 R1 실행 설정과 구분한다. 상세와 미실행 검증 경계는 [R1 보드 단계 도입](R1_PUZZLE_PROGRESSION_V3.md)에 있다.

학습 계획 상태는 별도로 관리한다. 원본 청사진의 구조 후보와 수정 필요 상태는 실제 문항 작성 완료를 의미하지 않는다. R1/R2 overlay만 실제 문장·힌트·해설·의미 profile을 공급하며, 미작성 리전의 복습 슬롯이 앞선 미완성 경로를 소급해 준비 완료로 바꾸지 않는다.

## 2. 학습 진행 원칙

각 챕터의 10개 슬롯은 다음 흐름을 기본으로 한다.

`선수개념 확인 → 개념 소개 → 안내 연습 → 독립 연습 → 가까운 전이 → 간격 복습 → 표현 전이 → 먼 전이 → 누적 확인 → 관문`

- 완료하면 도움 사용 여부와 관계없이 다음 스테이지를 연다.
- 2단계 이상 수학 힌트, 오개념 또는 첫 유효 제출 실패가 있으면 진행을 막지 않고 +1/+3/+7/+15/+35 간격의 단일 ticket 체인으로 복습한다.
- 일반 복습은 +2/+6/+15/+35/+75 간격으로 진행하며, 성공할 때 다음 ticket 하나만 만든다.
- 숙련은 한 번의 정답이나 별로 판정하지 않는다. 서로 다른 변형의 무힌트 성공 2회, 전이 성공과 최소 +15 지연 복습 성공이 필요하다.
- 발굴 보드 경로 힌트와 수학 힌트는 별도로 기록하며, 보드 실패는 수학 숙련을 낮추지 않는다.
- C04~C06은 고정 번호를 가진 권장·선택 숙련 경로다. 플레이 결과로 예약되는 복습 ticket은 번호가 없는 적응형 짧은 문제이며 420개 수에 포함하지 않는다.

실제 학습 지원 schema와 검증 기준은 [LEARNING_PROGRESSION_DESIGN.md](LEARNING_PROGRESSION_DESIGN.md)에 정의한다.

C01~C03 코어는 기존 난도 metadata를 보존한다. 고급 효과는 수학 난도가 안정된 stage에서 처음 소개하며, C05는 해당 효과가 전역 최초이면 `소개 → 안내 → 독립`, 이미 배운 효과이면 `회복 → 복습 → 독립`으로 시작해 마지막에 두 효과를 조합한다. C06은 그 조합을 교차 적용하는 슬롯이다. R1 C04~C06의 문항, 2층 봉인과 직선 파워는 구현되어 있다. 다른 리전의 효과는 엔진·adapter·fixture가 모두 준비되기 전에는 `playable`이 될 수 없다.

기존 `CHAR_A`~`CHAR_Z` 26명은 7개 리전의 `featuredCharacterIds`에 한 번 이상 모두 배정했다. 이는 상점 보유 여부와 별개인 지역 등장 역할이며, 선택 캐릭터와 지역 대표 캐릭터를 지도·힌트·완료 연출에서 함께 사용할 수 있게 한다.

## 4. 난도 의미

- `M0~M4`: 수학적 추론과 전이 난도
- `B0~B4`: 기본 보드 부담과 계획 깊이. 실제 효과 종류는 `BoardMechanicPlan`으로 별도 관리
- `C0~C3`: 정답식 길이, 괄호와 연산 결합 복잡도
- `R0~R2`: 문장 길이, 조건 수와 시각 자료 해석 부담
- `W`: 검증해야 할 기준 풀이 이동 수
- `P`: 탐색 별을 받을 수 있는 권장 이동 수
- `L`: 실패 처리 전 최대 이동 수

W/P/L은 현재 콘텐츠 설계 목표값이다. solver와 실제 사용자 풀이에서 측정된 값이 아니므로 fixture 제작 후 조정해야 한다. 5×5와 6×6은 서로 다른 난도가 아니며 같은 W/P/L을 충족해야 한다.

## 5. 문제 제작 경계

### 전체 앱의 문장 → 관계 → 식 연속성

`sentence_math_curriculum.dart`의 21개 핵심 해석 목표를 모든 420개 슬롯의 `SentenceMathPlan`에 연결한다. R1은 수량·묶음·연산 순서, R2는 변화 규칙·입출력, R3은 단위·단위당 양, R4는 반대 관계·미지량·균형, R5는 경계·면·공간, R6는 기준량·비율·자료, R7은 앞선 관계의 선택·통합으로 이어진다. 지역이 바뀔 때 이전 관계를 새 상황으로 연결하는 `bridgeGoal`을 유지한다. C04~C06은 source의 실제 개념을 승계하며, C05의 보드 효과 도입을 새 수학 개념 도입으로 오인하지 않는다.

실제 문항은 `SentenceMathProblem`의 주어진 조건, 구할 대상, 숨겨진 관계 설명, 의도한 정답식과 의미 profile을 함께 작성한다. R1 기존 문장은 호환 adapter로 같은 구조를 사용하며, 문제 크게 읽기에서는 조건과 구할 것만 구분한다. 관계 설명은 기존 관계 힌트, 정답식은 실제 AST·고유 토큰·정답 판정과 연결한다. 숫자가 커지거나 문장이 길어지는 것만으로 후반 난도를 만들지 않는다. 본문은 기본 120자·조건 문장 4개 이내를 유지하며, 복잡한 자료는 별도 renderer와 접근성 설명을 구현한 뒤 사용한다.

`SentenceMathValidator`는 문장/표시 내용, 의미 profile, 관계 힌트, 정답식·manifest·허용 AST가 연결되는지 검사한다. 캠페인 검사와 runtime 진입에서 같은 검사를 사용한다. 현재 표시 기능은 문장과 텍스트 기록뿐이며, 기록의 이름에 '표'가 들어간다는 이유로 시각 표·도형 기능이 구현된 것으로 취급하지 않는다. R4의 모르는 양을 구하는 숫자식은 현재 엔진으로 표현할 수 있지만, 변수·등호를 직접 조립하는 입력 방식은 별도 구현 대상이다. 자연어가 관계를 정확히 설명하는지는 자동 검사만으로 보장하지 않으며 편집자 검토와 사람 플레이가 필요하다.

이번 공통 구조 변경과 새 회귀 테스트는 코드 수정 범위로 진행했다. `flutter analyze`, `flutter test`, 실행·빌드 및 기기 검증은 별도 승인 후 수행한다.

각 stage의 `conceptLabel`은 최종 사용자 문장이 아니라 대표 문제와 의도한 답식이다. 실제 제작에서는 하나의 `skillId` 아래에 seed 기반 문장·숫자 변형을 만들되 다음 조건을 유지한다.

1. 정답 AST 구조와 교육 목표가 바뀌지 않는다.
2. 모든 숫자·기호는 고유 token instance를 가진다.
3. 나눗셈은 0 나누기와 의도하지 않은 비정수 결과를 차단한다.
4. 단위·도형·표는 시각 자료와 같은 의미의 스크린리더 설명을 함께 제공한다.
5. B3·B4가 필요한 stage는 해당 엔진과 fixture가 완성되기 전 `playable`로 승격하지 않는다.
6. 도형·좌표·표·그래프를 쓰는 stage는 해당 renderer와 같은 의미의 접근성 설명까지 구현한다.
7. 수학 연산 수·연산자 종류·괄호·연산 순서 metadata는 설명 전체가 아니라 `→` 뒤의 의도한 답식만 기준으로 계산한다.
8. B3의 2층 봉인과 먼지 장애물은 stage별 규칙으로 명시하고 번호 홀짝으로 추론하지 않는다.
9. 한 단계에서 M과 B를 동시에 올리지 않으며, B3·B4 최초 소개는 M0~M1 문제로 제한한다.
10. `planned → puzzleReady → playable` 승격은 문제 manifest, 필요한 renderer, compact/standard fixture, 회귀 seed 검증 순서로 진행한다.
11. `puzzleReady` 이상은 관찰→관계→부분식 3단계 힌트, 모든 오개념 범주 피드백, 최소 2단계 풀이 해설과 전이 문제를 가져야 한다.
12. 학습 계획이 `authored`가 아니면 문제·보드가 준비되어도 플레이 가능 상태로 승격하지 않는다.
13. 같은 skill의 독립 변형은 최소 두 교육 차원이 달라야 하며, 그중 하나는 문맥·표현·미지수 위치·정답 AST여야 한다.
14. stage ID, 보드 seed, 캐릭터 이름이나 표면 명사만 바꾼 문제는 숙련 증거로 인정하지 않는다.
15. 새 보드 효과는 단독 소개 전에 조합할 수 없고, 지역 외형이 달라도 같은 mechanic ID를 사용한다.
16. 의미 profile의 피연산자는 실제 정답식에서 산출하고, 문맥은 표면 명사가 아니라 작성된 상황 schema의 명시적 `contextFamilyId`, 표현은 연결된 renderer ID를 사용한다. phase·chapter 이름만으로 변형을 자가 선언하지 않는다.
17. C06의 교차 리전 강화 개념은 실제 문장과 정답 AST가 두 개념을 요구할 때만 `reinforcedSkillIds`와 숙련 증거에 넣는다.

## 6. 제작 우선순위

1. R2 C3, R4 C1, R5 C3, R6 C3의 개념 묶음과 관문을 재구성한다.
2. R1 첫 챕터 10개의 실제 Puzzle·토큰·힌트·오개념·해설·전이 문제를 작성한다.
3. R1 첫 챕터의 B0~B2 5×5·6×6 fixture를 만들고 W/P/L을 실측한다.
4. 같은 과정을 R1의 나머지 코어 챕터와 C04 나선 복습으로 확장한다.
5. 수열·입출력표 renderer를 추가한 뒤 R2의 B1~B2 구간을 제작한다.
6. 단위 metadata, 도형 diagram, 표·그래프 schema를 순서대로 추가한다.
7. B3 2층 봉인·먼지 장애물과 B4 4매치 특수 타일을 구현한다.
8. R7은 앞 6개 리전의 검증된 학습 개념과 renderer만 재사용해 제작한다.
