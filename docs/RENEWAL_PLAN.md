# KVM Flutter 리뉴얼 계획

## 1. 목표

리뉴얼의 목표는 기존 화면을 그대로 복제하는 것이 아니라 “매치 퍼즐로 숫자·기호를 발굴하고 문장을 식으로 바꾸는 수학 퍼즐”을 재현 가능하고 검증 가능한 Dart 엔진 위에 다시 만드는 것이다. 발굴 퍼즐의 상세 규칙과 FHD 화면 기준은 [DISCOVERY_PUZZLE_DESIGN.md](DISCOVERY_PUZZLE_DESIGN.md)에, 현재 7리전·420스테이지 구성은 [REGIONAL_STAGE_CURRICULUM.md](REGIONAL_STAGE_CURRICULUM.md)에 정의한다. 학습 역할·힌트·복습·숙련 기준은 [LEARNING_PROGRESSION_DESIGN.md](LEARNING_PROGRESSION_DESIGN.md)를 따른다. [STAGE_DIFFICULTY_DESIGN.md](STAGE_DIFFICULTY_DESIGN.md)는 초기 30스테이지 파일럿 기록으로 유지한다.

핵심 목표:

1. 모든 활성 문제가 실제로 풀릴 수 있어야 한다.
2. 동일한 seed와 콘텐츠 버전으로 문제를 재현할 수 있어야 한다.
3. 정답 값뿐 아니라 문법, 토큰 수량, 교육 목표 식 구조를 검증해야 한다.
4. 진행도와 보상은 원자적으로 저장되고 마이그레이션 가능해야 한다.
5. 휴대폰·태블릿·웹에서 읽기 쉽고 조작하기 쉬워야 한다.
6. 샘플 화면을 고정 데이터로 언제든 캡처할 수 있어야 한다.

## 2. 설계 원칙

### 2.1 계층 분리

Flutter 위젯과 퍼즐 규칙을 분리한다.

- domain: 수식 AST, 정확한 수, 토큰, 템플릿, 생성 규칙
- application: 퍼즐 세션, 제출, 힌트, 진행도, 보상 유스케이스
- infrastructure: JSON 카탈로그, 로컬 저장, 마이그레이션
- presentation: 화면, 컴포넌트, 애니메이션, 접근성

퍼즐 엔진은 Flutter import 없이 순수 Dart로 테스트 가능해야 한다.

### 2.2 단일 진실 원천

문장, 변수 제약, 정답, 정답 블록, 힌트, 난도, 카테고리를 하나의 PuzzleTemplate에 통합한다. 정답 공식이 별도 파일에 복제되지 않도록 한다.

### 2.3 재현 가능한 생성

stageId, templateId, contentVersion, attemptIndex를 기반으로 seed를 만든다. 생성 결과에는 seed와 변수 값을 저장하여 오류를 재현할 수 있게 한다.

### 2.4 블록 인스턴스 보존

화면에 같은 “3”, “×”, “(”가 여러 개 있어도 각각 고유한 tokenInstanceId를 가진다. 표시 문자열 기준의 distinct 처리는 금지한다.

### 2.5 정확한 수와 AST

정답은 Int 하나가 아니라 수식 AST와 정확한 유리수 값으로 관리한다. 부동소수점 반올림이 필요한 문제는 템플릿에 허용 오차와 표시 규칙을 명시한다.

## 3. 이번 vertical slice

이번 단계는 전체 월드맵이나 303개 문제 이식이 아니라 핵심 퍼즐 한 판을 완결하는 P0 vertical slice다.

### 현재 상태

- Android와 Web Flutter 대상이 생성되어 있다. Windows 데스크톱 대상은 없다.
- 고유 ID 토큰, 정확한 유리수, 수식 AST, 검증기, 5개 고정 샘플 문제, 퍼즐 화면 코드의 초기 구현을 완료했다.
- 결정론적 매치-3, 낙하·보충·연쇄, 숫자·연산자 봉인 발굴 엔진의 초기 구현을 완료했다.
- 800×360·720×320 및 SafeArea 후 680×300의 초광폭 저높이 화면에서는 5×5, 너비 720dp·높이 400dp 이상에서만 6×6을 사용하는 가로 3영역 화면을 추가했다.
- 질문의 묶음 관계를 보여 주는 `상자 3개 × 연필 4자루 + 낱개 2자루` 도식과 text scale 130%용 compact 글자 규칙을 추가했다.
- 첫 프로토타입은 `4`, `3`을 먼저 제공하고 세 번의 검증된 매치로 `×`, `+`, `2`를 하나씩 발굴한다. 5×5와 6×6은 독립 fixture ID와 seed를 사용하되 같은 경로와 W/P/L을 만족한다.
- 첫 튜토리얼 동안에는 현재 단계의 안내 교환만 받아들여 보드 변형 후 고정 안내가 틀려지는 경로를 막는다. 일반 스테이지에서는 이 제한을 사용하지 않는다.
- 발굴 결과를 기존 AST·정확한 유리수 정답 검증으로 연결하는 통합 ViewModel을 추가했다.
- 발굴 엔진 상태를 캐시하고 refill 예외가 화면에 이동 수·수집 조각만 부분 반영하지 않도록 커밋 시점을 뒤로 옮겼다.
- `1스테이지 = 문장제 1개 + 보드 1개`로 캠페인 단위를 정하고, 7리전마다 C01~C03 코어와 C04~C06 나선 경로를 둔 420개 M/B/C/R·W/P/L 카탈로그를 추가했다.
- 기존 코어 210개의 `stageId`·`skillId`·puzzle ID·seed·fixture ID는 보존했다. C04 재인출, C05 보드 효과 학습, C06 장기 유지·교차 전이 슬롯 210개는 코어 source를 한 번씩 다시 참조한다.
- 코어에서는 개념 구성이 분산됐거나 변형·전이 기회가 부족한 86개가 `requiresRevision`, 나머지 124개가 구조 후보 `planned`다. 추가 210개는 실제 새 숫자·문맥·표현이 미작성이라 모두 `requiresRevision`이며, 전체는 296개 `requiresRevision`, 124개 `planned`다.
- C03 S10은 현재 리전 C04와 다음 리전을 함께 열고, C06 S10은 지역 숙련 완료로 끝난다. v3 저장에서 이미 완료한 C03 해금은 v4 순수 migration이 다시 계산한다.
- 일반 +2/+6/+15/+35/+75, 지원 필요 +1/+3/+7/+15/+35의 적응형 복습은 번호가 있는 420개 경로와 별도 ticket 체인으로 관리한다.
- stage ID나 seed가 아닌 실제 문제의 의미 fingerprint가 달라야 독립 성공·전이·지연 복습 증거로 누적된다.
- 프로토타입에는 관찰→관계→부분식 힌트, 오류 범주별 피드백, 2단계 풀이 해설과 전이 문제를 작성했다.
- 완료 시 다음 스테이지를 열고, 도움·오개념에 따라 복습을 예약하며 서로 다른 변형의 독립 성공과 지연 복습으로 숙련을 판정하는 순수 Dart 엔진을 추가했다. 실제 저장·월드맵·완료 버튼 연결은 아직 없다.
- 캠페인 계층은 `Campaign → Region → Chapter → Stage`이며, 리전에는 기존 ID, 정규화 hotspot, 배경·오버레이·뱃지 asset key와 대표 캐릭터 ID가 있다.
- 5×5·6×6은 난도 단계가 아니라 같은 목표와 이동 예산을 유지하는 독립 fixture로 정의한다.
- 완료·첫 의미상 제출·수학 힌트·사용 이동·경로 힌트를 입력으로 완료/수학/탐색 별을 각각 판정한다.
- 현재 통합 ViewModel의 고정 문제·12회 이동·seed·토큰 목록을 제거하고, 별도 프로토타입 `StageDefinition`에서 해당 설정을 주입한다. 플레이 화면은 한 스테이지임을 반영해 기존 `1/5` 대신 수학/퍼즐 난도를 표시한다.
- Semantics, 터치 영역, 포커스 순서, 상태 안내를 포함한 기본 UI 접근성 처리의 초기 구현을 완료했다.
- 순수 Dart 수식 엔진, 발굴 엔진, 캠페인 카탈로그 검증은 통과했다.
- 800×360·720×320 및 SafeArea 후 680×300의 초기 5블록 화면은 치수 계산상 질문·도식·5×5 보드·수식·액션이 함께 들어간다. 680×300에서도 보드 셀은 약 44dp를 유지한다.
- Flutter analyze·test·run과 Android·Chrome 수동 플레이는 이번 문서 시점에 수행하지 않았다.
- 초기·식 구성·문법 오류·오답·힌트·정답 상태별 독립 fixture와 golden 테스트는 아직 구현되지 않았다.
- 따라서 아래 항목은 구현 완료 보고가 아니라 vertical slice의 범위와 완료 기준이다.

### 3.1 포함 범위

- Flutter 앱의 기본 테마와 퍼즐 플레이 진입 화면
- 문장 문제 카드
- 인접 교환, 3개 이상 매치, 낙하·보충·연쇄가 가능한 발굴 보드
- 보석 아래 숫자·연산자 봉인과 획득 보관함
- 풀이 식 보드
- 고유 ID를 가진 숫자·연산자·괄호 블록 은행
- 탭으로 추가, 제거, 순서 변경, 전체 초기화
- 문법 파싱과 AST 생성
- 정확한 값 계산과 정답 판정
- 잘못된 문법, 0 나눗셈, 미완성 식의 구체적 오류 표시
- 관찰→관계→부분식의 타입 있는 단계형 힌트
- 오개념별 피드백, 정답 후 단계 해설과 전이 문제
- 고정 fixture 샘플 문제
- 휴대폰과 넓은 화면의 반응형 배치
- 질문·상황 아이콘, 발굴 보드, 정답 공간의 가로 3영역 동시 노출
- 주요 버튼 최소 48dp, compact 보드 타일 44dp 목표·40dp 하한, 의미 있는 Semantics, 충분한 색 대비
- 캡처를 위한 고정 샘플 상태

샘플 템플릿은 엔진의 핵심 위험을 검증하도록 구성한다.

1. 곱셈과 덧셈이 섞인 묶음 문장제
2. 괄호가 필요한 직사각형 둘레
3. 같은 숫자 블록 두 개가 필요한 정사각형 넓이
4. 시간 단위 변환
5. 합과 차를 이용한 관계식

### 3.3 vertical slice 완료 기준

기능:

- 같은 표시값의 블록 두 개를 서로 독립적으로 사용할 수 있다.
- 유효한 식만 AST로 변환된다.
- 마지막 AST가 하나가 아니거나 괄호가 맞지 않으면 제출되지 않는다.
- 0 나눗셈은 앱 크래시 없이 명시적 오류가 된다.
- 정답 식과 값이 맞으면 완료되고, 틀리면 현재 시도를 유지한 채 피드백을 준다.
- 힌트는 정답을 즉시 노출하지 않고 단계적으로 구체화된다.
- reset과 다음 샘플 진입이 예측 가능하게 동작한다.

품질:

- 핵심 엔진은 순수 Dart 단위 테스트를 갖는다.
- 중복 토큰, 연산 우선순위, 괄호, 나눗셈, 미완성 식 회귀 테스트를 갖는다.
- 고정 fixture로 매번 동일한 문장·숫자·블록을 재현한다. seed 생성기는 P1에서 추가한다.
- 작은 휴대폰 폭과 태블릿·웹 폭에서 오버플로가 없다.
- 키보드 포커스와 스크린리더용 라벨이 제공된다.
- 로딩·빈 상태·오류 상태를 구분한다.

검증과 산출물:

- dart format 대상 파일이 정리되어 있다.
- flutter analyze와 관련 테스트가 통과한다.
- Android 또는 Chrome에서 수동 플레이가 완료된다.
- 기본, 식 구성 중, 오답, 힌트, 정답 상태의 샘플 캡처가 생성된다.

Flutter 명령 실행은 프로젝트 규칙에 따라 사용자 승인 후 수행한다.

## 4. P1 로드맵: 엔진과 활성 콘텐츠 기반

목표는 기존 StageManager가 실제 참조하는 47개 템플릿을 안전하게 이식할 수 있는 구조를 만드는 것이다.

### 범위

- domain/application/infrastructure/presentation 폴더 분리
- PuzzleTemplate JSON schema v1
- 변수 생성 제약과 seed 기반 생성기
- 수식 AST, 정확한 유리수, 검증 결과 모델
- 템플릿별 정답 AST와 블록 인벤토리
- 타입 있는 단계형 힌트, 오개념 피드백, 풀이 단계와 전이 문제 모델
- 콘텐츠 카탈로그 로더
- 카탈로그 정적 검증 CLI 또는 테스트 도구
- 현재 세션 로컬 저장
- 사용자 프로필과 스테이지 진행 저장 schema v1
- 활성 47개 템플릿의 검증·격리·승격
- R1 계산의 평원 코어 B0~B2 30개와 연결된 C04 의미 변형을 실제 문제·fixture로 우선 승격하고 순차 해금
- R1 각 챕터의 선수확인→소개→안내→독립→전이→복습→관문 학습 흐름 작성
- 완료 스테이지 수 기반 복습 큐, 도움 증거와 숙련 상태 저장
- 나머지 코어 180개와 미작성 나선 200개는 필요한 수학 콘텐츠·매치 규칙·renderer가 준비될 때까지 비활성 상태 유지

### 완료 기준

- 활성 템플릿 ID가 모두 카탈로그에 존재한다.
- 각 템플릿이 1,000개 이상의 seed 표본에서 예외 없이 생성된다.
- 모든 생성 결과에서 placeholder가 남지 않는다.
- 정답 AST가 생성 변수만 참조한다.
- 정답 블록 멀티셋으로 canonical AST를 구성할 수 있다.
- 분모가 0이 되지 않는다.
- R1 코어 30개 모두 실제 Puzzle·토큰 manifest를 가지며 B0~B2 범용 파이프라인으로 실행된다.
- R1 C04의 source-linked 문제는 실제 피연산자와 문맥 또는 표현이 달라 의미 변형 검증을 통과한다.
- R1 각 stage의 5×5·6×6 fixture가 solver 기준 경로로 검증되고, 실측 W에 맞춰 P/L이 조정된다.
- R1 각 stage에 3단계 힌트, 주요 오개념 피드백, 최소 2단계 해설과 전이 문제가 있고 validator를 통과한다.
- 완료하면 다음 stage가 열리고, 도움을 받은 완료도 진행을 막지 않은 채 복습 큐에 기록된다.
- 서로 다른 변형의 무힌트 성공 2회와 지연 복습 성공 없이 숙련 상태가 되지 않는다.
- 위 조건을 통과한 R1 stage만 `planned → puzzleReady → playable` 순서로 승격된다.
- 저장 후 앱 재시작 시 같은 세션과 seed를 복원한다.
- 진행 저장과 보상 갱신이 한 트랜잭션으로 처리된다.

목표는 핵심 퍼즐을 반복 플레이 가능한 제품 흐름으로 확장하는 것이다.

### 범위

## 6. P3 로드맵: 전체 콘텐츠·최적화·출시

목표는 최신 APK의 303개 템플릿을 검증된 콘텐츠로 승격하고 출시 품질을 확보하는 것이다.

### 범위

- 303개 전체 템플릿 변환
- 미지원 문제의 격리와 콘텐츠 수정 이력
- 도형·표·그래프 전용 시각 자료
- 분수·소수·비율·방정식 표현 확장
- 전체 캐릭터·뱃지 에셋 정리
- 성능 프로파일링과 이미지 최적화
- 앱 시작 시간, 메모리, 프레임 드롭 개선
- 저장 백업·복구와 선택적 클라우드 동기화 검토
- 오류 진단용 익명 seed·templateId 기록
- 플랫폼별 회귀 테스트
- 접근성·현지화·개인정보·스토어 체크리스트

### 완료 기준

- 303개 원본 ID가 migrated, quarantined, retired 중 하나로 모두 분류된다.
- migrated 템플릿은 자동 생성·풀이 가능성 검사를 통과한다.
- quarantined 템플릿은 사용자 경로에서 선택되지 않는다.
- 주요 화면의 골든 이미지와 실제 기기 캡처가 승인된다.
- 성능 예산과 앱 용량 목표를 충족한다.
- 저장 마이그레이션 실패 시 원본을 보존하고 복구할 수 있다.

## 7. 데이터 이식 전략

### 7.1 원본 동결

1. KvMA_2.1.apk 원본과 SHA-256을 기록한다.
2. APK에서 assets/problems.json을 추출해 원본 그대로 보존한다.
3. loose GameData 296개, ProblemLogicManager 296개, StageManager 활성 47개를 별도 목록으로 추출한다.
4. 네 집합의 ID, 문장, 변수, 설명, 힌트 차이를 보고서로 만든다.

원본 JSON은 직접 수정하지 않고 derived 카탈로그를 새 파일로 생성한다.

### 7.2 정규 스키마

PuzzleTemplate의 최소 필드:

- id
- schemaVersion
- contentVersion
- legacySource
- category
- difficulty
- promptTemplate
- variableSpecs
- constraints
- answerAst
- canonicalTokens
- allowedEquivalentForms
- hintSteps
- explanation
- tags
- status

status는 draft, active, quarantined, retired 중 하나다.

### 7.3 변환 규칙

- Kotlin 람다를 런타임에서 실행하거나 문자열 eval로 옮기지 않는다.
- 정답 공식은 타입이 있는 AST로 수동 또는 검증된 변환을 거친다.
- 변수 생성 범위와 정답의 정수·분수 조건을 템플릿에 명시한다.
- 텍스트 치환용 컴포넌트와 수치 변수를 구분한다.
- 같은 텍스트 블록도 수량을 보존하는 멀티셋으로 변환한다.
- 기존 ID를 안정적으로 유지하고 새 ID가 필요하면 legacyId 매핑을 둔다.

### 7.4 단계적 승격

1. vertical slice 샘플 5종
2. StageManager 활성 47종
3. 각 카테고리 대표 확장 문제
4. 303종 전체

자동 검증을 통과하지 못한 문제는 active로 올리지 않는다.

## 8. 데이터 검증 전략

### 8.1 정적 검증

- ID 중복과 빈 ID
- 스테이지 참조 누락
- 정의되지 않은 카테고리
- placeholder와 variableSpecs 불일치
- answerAst의 미정의 변수 참조
- 토큰 멀티셋 부족
- 빈 힌트·해설
- 잘못된 난도 범위
- retired·quarantined 템플릿의 활성 경로 참조

### 8.2 생성 기반 검증

템플릿마다 최소 1,000개 seed를 생성해 다음을 검사한다.

- 예외 없이 생성되는가
- 모든 제약을 만족하는가
- 0 나눗셈이 없는가
- 정확한 값 범위가 허용되는가
- 문장에 placeholder가 남지 않는가
- canonicalTokens로 answerAst를 만들 수 있는가
- 방해 블록이 정답 블록을 제거하지 않는가
- 최소 하나의 유효 풀이가 존재하는가

실패 로그에는 templateId, contentVersion, seed, 변수, AST, 토큰 목록을 남긴다.

### 8.3 회귀 검증

- 과거에 실패한 seed를 fixture로 고정한다.
- 303개 원본 ID와 변환 상태 manifest를 스냅샷 테스트한다.
- 카탈로그 변경 시 문제 수와 상태별 수량 변화를 리뷰한다.

## 9. 저장과 마이그레이션 전략

### 9.1 신규 저장 모델

저장은 버전이 있는 SaveEnvelope로 감싼다.

- schemaVersion
- contentVersion
- profile
- stageProgress
- activeSession
- inventory
- achievements
- counters
- migratedFrom
- updatedAt

별은 다음 두 값으로 분리한다.

- lifetimeStarsEarned: 업적·진행 해금용 누적값
- spendableStars: 캐릭터 구매용 잔액

### 9.2 원자적 갱신

스테이지 완료 시 다음 값을 하나의 repository transaction으로 갱신한다.

1. 스테이지 최고 별
2. 누적·소비 가능 별
3. 문제 유형 해결 수
4. 사용 블록 수
5. 완벽 클리어 수
6. 업적 이벤트
7. 활성 세션 종료

중간 실패 시 전체를 롤백하거나 재시도 가능한 이벤트를 남긴다.

### 9.3 세션 복구

activeSession에는 stageId, problemIndex, templateId, seed, 생성 변수, token instances, 현재 식 순서, 오답 수, 힌트 단계, 패스 여부를 저장한다.

앱 재시작 후 contentVersion이 같으면 정확히 복원한다. 콘텐츠가 바뀌어 복원이 안전하지 않으면 기존 세션을 보관한 채 사용자에게 새로 시작할지 안내한다.

### 9.4 마이그레이션

- 모든 schema migration은 v1→v2처럼 순차적 순수 함수로 작성한다.
- migration 전 원본 payload를 백업한다.
- 각 버전별 fixture와 실패 복구 테스트를 둔다.
- 알 수 없는 미래 버전은 파괴적으로 초기화하지 않는다.
- contentVersion migration과 save schema migration을 분리한다.

기존 Room DB를 Flutter 앱이 자동으로 직접 읽는 것은 별도 네이티브 브리지와 기존 앱 업데이트 경로가 필요하다. 배포 연속성이 중요하면 기존 Android 앱에 1회성 JSON export를 추가하고 신규 Flutter 앱이 서명·버전 검증 후 import하는 방식을 사용한다. 그 경로를 제공할 수 없다면 신규 앱은 새 저장으로 시작하며, APK 데이터와 사용자 진행 데이터의 이식 가능 여부를 명확히 구분한다.

## 10. 캡처와 시각 검증

현재 신규 Flutter 화면 캡처는 생성하지 않았다. 대화에서 조작 가능한 FHD 설계 프리뷰는 준비했지만 Flutter 렌더 결과가 아니므로 기기 캡처를 대신하지 않는다. Android와 Chrome/web에서 고정 샘플 문제를 열 수 있는 소스 기반은 마련되어 있으나, 실행 검증과 상태별 fixture·golden은 미완료다.

향후 고정 fixture를 우선 사용하고 P1 seed 생성기가 준비되면 seed까지 함께 기록하여 다음 캡처를 재현한다.

| 상태 | 목적 |
| --- | --- |
| initial | 정보 위계와 첫 행동 확인 |
| composing | 블록 가독성과 순서 변경 확인 |
| invalid | 문법 오류 표현 확인 |
| incorrect | 오답 피드백 확인 |
| hint-1, hint-2 | 힌트 단계 확인 |
| correct | 성공 피드백 확인 |
| compact | 작은 휴대폰 레이아웃 확인 |
| wide | 태블릿·웹 레이아웃 확인 |

파일명 예:

kvm_puzzle_composing_844x390_fixture-p1_v1.png

캡처와 golden 테스트는 같은 fixture를 사용하도록 설계한다. 이 fixture 카탈로그와 golden 기준 이미지는 아직 생성하지 않았다.

## 11. 용량 정리 전략

정리는 구현과 병행하되 삭제 순서를 지킨다.

1. 파일 해시와 참조 목록 생성
2. 최신 APK·JSON·원본 에셋 보존
3. 신규 앱에서 실제 사용 에셋 확인
